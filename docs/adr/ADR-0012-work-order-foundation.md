# ADR-0012 — Work-order foundation: operator maintenance records + the one-transaction return-to-service orchestration, NO computed Part-43 determination

**Status:** Accepted (Phase 4 entry, Slice M1 / MAINTENANCE-M1; ratified by conductor 2026-06-19). **Owners:** architect, compliance-officer, backend-engineer. **Builds on:** ADR-0001 (RLS/`withOrgContext`), ADR-0003 (capability gate), ADR-0007 (dispatch records — the write-once + terminal-shape posture), ADR-0008 (grounding/squawks — FROZEN gate; this slice reuses its WRITE paths), ADR-0011 (training records — the operator-data-not-FAA-determination line). Additive; modifies no existing engine.

## Context
M1 opens the Maintenance hub with the first thing downstream of a squawk/grounding: a **work order**. The compelling loop the incumbents bury behind paperwork: a grounded aircraft → open a work order → record the work + a sign-off → complete → the squawk resolves and the aircraft returns to service. Two structural problems: (1) maintenance records are the deepest FAA-compliance minefield (Part 43 §43.9/§43.11 return-to-service, airworthiness, A&P/IA sign-offs) — the software must record operator data and compute **no** determination; (2) "complete the work order, resolve the squawk, unground the aircraft" spans three existing write paths and must be **atomic** (no half-applied loop) while reusing — not forking — the FROZEN grounding/squawk logic.

## Decision

### 1. Data-only posture — a work order is an operator maintenance record, NOT a Part-43 determination
A `work_order` is operator content + instructor/mechanic DATA ENTRY: free-text `title`/`description`/`work_performed`/`sign_off_notes` (parts & labor are free-text notes ONLY — NO parts table, NO labor lines, NO money), an operator-defined status (`open → in_progress → completed | cancelled`), and a **sign-off** (`signed_off_by`/`signed_off_at`/`sign_off_notes`) that is a recorded operator action — **NOT** an A&P/IA digital certification, **NOT** an e-signature, **NOT** credential-verified (the signer is ANY org member with the cap). The software computes/asserts **no** airworthiness, return-to-service (§43.9/§43.11), AD compliance, inspection currency (annual/100-hr/§91.409), or MEL status. `status='completed'` is a content-state flag, never a computed RTS. The completion dialog AND the detail page carry the mandatory verbatim disclaimer ("…NOT an FAA return-to-service or §43.9/§43.11 determination, and the system makes no airworthiness determination"). Compliance PASS (M1).

### 2. Records integrity — terminal fields write-once; terminal states have no reopen (mirrors ADR-0007/0011)
The sign-off/work-performed/cancelled fields are immutable once the work order is `completed`/`cancelled` — guarded by every write path's `WHERE status IN ('open','in_progress')` clause (a terminal row updates 0 rows → `not_completable`/`not_cancellable`) plus `work_order_completed_shape_check` (completed ⇒ `signed_off_at` NOT NULL; cancelled ⇒ `cancelled_at` NOT NULL; open/in_progress ⇒ all sign-off/cancel fields NULL). No reopen path exists ([VERIFY-M1-B]); a future correction is an append-only record, never an edit. `signed_off_by` is `ON DELETE SET NULL` (column-list, so `org_id` is preserved) and intentionally excluded from the shape CHECK's NOT-NULL arm — the durable "who signed" lives in `audit_log`. **Forward warning ([VERIFY-M1-C], in the schema doc + migration):** any Phase-4+ consumer attaching Part-43/A&P-IA meaning MUST preserve signer identity immutably, never via the SET-NULL column (mirrors `squawk.resolved_by`, `lesson_record.voided_by`).

### 3. The orchestration seam — extract tx-level inner cores; `completeWorkOrder` runs the loop in ONE transaction
`updateSquawkStatus` and `ungroundAircraft` each opened their own `withSessionOrgContextWithDb` transaction. To make the return-to-service loop atomic without forking logic, their callback BODIES were extracted into tx-scoped inner helpers in `maintenance/internal.ts` — `applySquawkStatusOnTx(sess, tx, …)` + `applyUngroundOnTx(sess, tx, …)` (each does its guarded write + its OWN audit row; no `requireCapability`, no context-open). The public `*`/`*WithDb` functions became thin wrappers that delegate — **byte-equivalent behavior; the existing squawk/grounding tests stayed green.** `completeWorkOrder` then runs the WO-complete + optional `applySquawkStatusOnTx` + optional `applyUngroundOnTx` **inside ONE transaction**: any throw rolls back the WHOLE loop (no half-applied state — atomicity-tested). The sub-action ids (`squawkId`, `resourceId`) come from the work-order row **read in-context**, never from caller input, so cross-org sub-mutation is structurally impossible. Idempotent skips (already-resolved squawk, not-grounded) are informational `ok:true` arms that write no audit and never fail completion. **The FROZEN grounding GATE (`evaluateGroundingGate`, ADR-0008), `gatedCreateOccurrence`, and `openDispatch` are untouched** — M1 orchestrates only the WRITE paths.

### 4. The unground rule — operator-convenience guard, never a computed clearance
`shouldUngroundForWorkOrder` (pure, `@aeroops/core`, unit-tested) releases the aircraft ONLY if it is currently grounded AND the latest grounding event's `squawkId` (additively projected onto `loadGroundingProbe`'s `GroundingProbeEntry`) equals the work order's `squawkId`; otherwise it declines with a skip reason (`not_grounded` / `grounded_for_other_reason` / `no_matching_grounding_basis`). Every decline path leaves the aircraft grounded — it never grounds or computes airworthiness. The operator must still affirmatively check the "return to service" box; the rule only prevents releasing an aircraft grounded for an unrelated reason ([VERIFY-M1-D]).

### 5. Capabilities + the conditional sub-caps
One new capability `maintenance:work_order` (open/advance/complete/cancel) → owner/manager/dispatcher/mechanic (NOT cfi/accountant/renter/student); reads reuse the existing `maintenance:access`. `completeWorkOrder` ADDITIONALLY requires `maintenance:squawk` when `resolveSquawk` and `maintenance:ground` when `unground` — checked UP FRONT before any write, so a role that cannot ground cannot unground via the work-order back door (the existing authorization boundary is preserved). `requireCapability` is the first statement in every `*Impl`; org_id from session only; one audit row per real mutation; `apps/web` never imports `@aeroops/db`.

### 6. Isolation invariants + deferred seams
`work_order`: `org_id` + FK→org CASCADE; composite FKs `(resource_id,org_id)` RESTRICT, `(squawk_id,org_id)` SET NULL, `(opened_by,org_id)` RESTRICT, `(signed_off_by,org_id)` SET NULL (all column-list where SET NULL); ENABLE+FORCE RLS; 4 fail-closed policies; `UNIQUE(id,org_id)`; `aeroops_app` grant. The Fleet-detail `openWorkOrders` facet is RLS-scoped and read-gated by `fleet:access` (parity with how squawks/grounding already surface) ([VERIFY-M1-E]). Migration **0013** + down staged with the human-gated banner, NEVER auto-applied; strictly additive. **M1 reads NO dispatch Hobbs/tach meters** — it references the aircraft + squawk + grounding only, so it does NOT trip the [[dispatch-correction-table-predecessor]]. **Deferred forward seams (built in NONE of M1, each its own slice + compliance pass):** A&P/IA credential verification, e-signature/cryptographic signing, AD / inspection-due / annual / 100-hr / §91.409 tracking, MEL, parts inventory, labor/maintenance billing, §43-compliant logbook records. NO money anywhere in M1.
